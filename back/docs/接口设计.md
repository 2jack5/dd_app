# 东东电竞APP后端接口设计 V0.2

依据用户提供的PRD、用户端/陪练师端/后台三张截图，以及当前55表模型设计。原PRD为小程序，本次兼容微信App和小程序身份；不扩展社交、IM、充值钱包和自由提现。

## 本轮复查结论与文档版本

三端板块与交易拆分方向合理，保留180个接口作为完整能力目录。业务契约沿用V0.2；本次按用户指定结构重建Kratos接口：cmd/server/main.go调用api.NewRouter，所有接口注册语句统一放在internal/api/router.go中并按板块分组；public.go、user.go、coach.go、admin.go、callback.go仅保留对应处理函数、请求结构和相关辅助函数。

此前router.go空文件造成的编译问题已解决。请求结构已按V0.2分别生成，但规划业务尚未绑定/验证请求或实现事务；不能把接口框架可启动理解为180项业务全部完成。没有额外保留上一轮biz/data/service/internal/server等转发层。

## 设计边界

- 当前为Kratos HTTP接口框架与接口规划，不是已完成的交易后端。180条路由中，进程存活、数据库连接检查以及游戏/区服/段位/分类查询共6条有实现链路；其余规划接口返回501，受保护接口在鉴权未配置时拒绝执行，渠道通知返回503。
- 路由直接使用Kratos Router，尚未生成protobuf、gRPC或Wire代码。`openapi.json`可导入Apifox/Swagger；请求结构是设计契约，尚未给规划接口生成字段绑定和业务验证。响应暂统一Envelope，具体业务响应DTO按用例逐步补全。
- 不按表逐一开放CRUD。入驻、审核、接单、退款、出款等用业务动作表达；不开放直接PATCH订单/支付成功状态或客户端自填佣金接口。

## 统一约定

路径前缀为 `/api/v1`，健康检查为 `/healthz`、`/readyz`。JSON统一 `{code,message,data,request_id}`；请求号由服务端生成，并通过 `X-Request-ID` 返回。列表结构 `{items,next_cursor}`，`page_size`默认为20、最大100。已实现目录查询用正序ID游标；其他排序需绑定筛选条件和完整排序键，不能复用不兼容游标。

ID用十进制正int64字符串，金额为整数分且计算防溢出，费率为整数万分比；版本/数量为正int32，时间使用RFC3339带时区格式，保存为UTC。身份从会话中获取，不接受客户端指定buyer_id、coach_id作为本人身份。

`date/from_date/to_date/bill_date`是日历日期，使用YYYY-MM-DD；排期和经营日按Asia/Shanghai解释，渠道账单日按账单约定时区解释，不能把日期当UTC时刻换算。区间统一半开 `[start,end)`，开始必须早于结束，设置最大查询跨度。

用户/陪练与后台分别使用Bearer凭据及独立签发受众。当前身份适配器未接入：无凭据返回401，带凭据但未配置验证服务返回503。后台还需动作权限与数据范围，工单还需本人/被分配资源归属校验。数据库封禁、资格过期及auth_version必须实时或通过可失效缓存生效。

需要幂等的用户/陪练/后台写操作要求 `Idempotency-Key`；当前仅检查键存在和长度，最终必须由事务内idempotency_keys记录参数哈希和结果，不可仅靠Header认为已幂等。登录/刷新、第三方回调采用各自的凭据轮换或通知去重机制。

错误使用400参数错误、401无效身份、403权限不足、404不存在、409业务状态/库存/版本冲突、501未实现、503依赖未配置或暂不可用；不返回原始数据库错误或DSN。

## 首期范围与增强项

180项是动作级能力目录，不是180个页面，也不代表必须同时开发。OpenAPI增加 `x-delivery-priority`：175项标P0，5项标P1。P1仅指本方案额外加入的手工正向资金修正/补款创建重试及补款列表；不包含原PRD要求的正常结算、退款、追偿、对账。DAU采集与在线心跳维持P0，以支持首期统计与在线展示。此分期为建议，不能自动缩减用户已确认的首期业务范围。

## 关键请求结构

完整字段见 `api/v1/openapi.json` 的 components.schemas；以下是业务约束：

|操作|主要输入|必须在事务/渠道中核对|
|---|---|---|
|报价|service_id、region_id、quantity、appointment_start_at|有效服务与认证、计价单位、时段、规则版本；不锁库存|
|下单|quote_no、game_player_id、remark、agreement_acceptance_id|报价归属和版本；锁陪练后校验排期，再写订单、占位、事件及Outbox；不信客户端金额|
|支付|订单路径与client_type|复用商户订单号，渠道验真；客户端支付成功不能推进订单|
|退款|amount_cent、reason_code、证据|批准时锁支付记录预留额度；成功通知才记退款与应结调整|
|提交完成|schema_version、completed_quantity、actual_end_at、证据、version|本人订单、已开始、时长/局数规则；用户确认前不当作最终完成|
|修改排期|date、expected_slots、slots|锁同一陪练，核对该日完整旧排期版本集合及全部已占时段|
|敏感审批|资源ID、版本、operation、parameters|服务端计算哈希、双人复核、批准有效期；执行时重核实际参数|
|独立补款|adjustment_id、account_id、approval_id|首次已出款、正向调整未使用、剩余应付和未终结预留；重试沿用原请求号|

按局服务以预约预计占用时间售卖时段；实际超时不能侵占下一单，需另行协调，不在原订单里静默延长。所有退款、结算和投诉冻结并发按模型说明中的统一锁顺序处理。

## 首期实现顺序

1. 账号登录、协议、私有上传、后台身份与RBAC；用户刷新凭据的撤销/轮换存储机制先确定，不能只签发永久token。
2. 陪练入驻、实名、技能审核，服务与排期；目录后台维护及首页发现。
3. 报价、预占、订单、支付验真、超时关单及接拒单。
4. 开始/提交完成/确认、退款预留、争议工单、评价内容审核。
5. 结算、补款、追偿、对账与财务复核；最后完善经营看板。

后台菜单可按截图的四个板块组织：人员与审核、商品与运营、交易与售后、财务与统计；权限与设置作为基础模块。目录里88条后台接口是动作级拆分，不等于85个页面或服务。

## V0.2 参数和流程契约（请求结构已定义，业务待实现）

### 1. 列表、详情和时间查询分开

只有真正的列表接受page_size/cursor。我的资料、单条详情、经营摘要、健康检查不再自动带分页参数。排期按业务date查询；统计按from_date/to_date查询，必须限制跨度。目录API当前ID游标是已存在处理代码的行为；按价格/评分排序的发现列表后续采用“筛选条件+完整排序键+ID”的游标，改筛选条件需重新分页。

用户和陪练订单支持履约状态筛选；退款与工单采用各自枚举，不把“退款中”塞进履约status。后台列表额外限定订单号、当事人、时间与处理人等白名单条件，不能把任意请求参数直接拼成SQL。

### 2. 找陪练的筛选规则

明确game_id、region_id、rank_id、unit_type、min_price_cent、max_price_cent、start_at、end_at、keyword、min_rating、online、accepting_orders、verified和sort。金额是非负整数分、评分范围1到5、开关是boolean、单位为HOUR/ROUND，排序只接受推荐/价格升降/评分降序。

价格必须与服务单位共同理解，不能直接把“每局30元”与“每小时30元”当作同一种单位比较；不同单位在列表明确展示。时间筛选须同时给start_at/end_at并校验覆盖与占用。online是心跳TTL结果，accepting_orders是接新单开关，二者不能混用；未显式筛选时仍排除无可售服务及不合格认证。列表只代表查询时可约，创建订单重新原子抢占。

### 3. 创建与PATCH分离

角色创建必须提供稳定code、name、data_scope、permission_ids、status；角色PATCH使用AdminRolePatch，不能改code，也不能因只改名称而被迫重传全部权限。修改角色权限后使所有受影响管理员旧权限失效。

资料和其他PATCH至少提供一个实际可修改字段；只传版本号的空修改应拒绝。省略表示不改，显式null仅允许在契约标nullable的可清除字段，不能把空字符串当作所有字段的删除动作。版本必须由详情/列表返回，客户端不能猜测。

### 4. 审核版本按实体定义，不虚构数据库列

|对象|并发前置条件|备注|
|---|---|---|
|入驻申请|expected_revision + expected_status|锁申请的提交版本；同一次提交不可覆盖已决结果|
|游戏技能|expected_revision + expected_status|审核后切换当前有效版本，保留旧历史|
|内容审核|expected_revision + source_version + expected_status|核对审核提交和业务内容版本；资源等不可变目标核对摘要，不要求所有目标都存在version列|
|实名人工复核|expected_status|锁渠道结果与核验引用，只记人工意见，不把渠道FAILED改成PASSED|
|敏感审批复核|expected_payload_hash + PENDING + 有效期|审批本身无version列；请求者不能审批本人|
|退款批准/拒绝|resource_version|对应refunds.version，批准前还须原子预留退款额度|
|撤销处罚|ACTIVE状态及锁定处罚ID|处罚表无version列；撤销后聚合剩余有效处罚|

业务对象的revision、内容版本、登录auth_version和并发version各有用途，不互相替代。驳回必须有对提交者可见的原因；内部风控备注不得通过用户进度接口泄露。

### 5. 先批准后创建资金记录的闭环

此前只写“创建需要approval_id”，容易导致新记录还不存在，却先要填审批resource_id。本版统一让**创建类财务批准绑定既有应结记录SETTLEMENT_ITEM**，不使用虚构ID，也不提前制造资金事实。

- 创建出款批次：先选择同陪练、同渠道/有效账户的既有应结项。审批锚点为排序后首个应结ID及其version；parameters必须覆盖全部明细的ID、version、金额、收款账户及账户版本/快照。至少1项、至多100项、不能重复。只核第一项版本不够。
- 创建资金修正：审批绑定所属既有应结ID及version，parameters固化全部带符号delta、原因、规则及依据；校验gross_delta等于commission_delta加coach_delta。退款调整仅由真实退款成功内部用例生成。
- 创建独立补款：审批绑定正向调整所属既有应结ID及version，同时固化adjustment_id、account_id、净增额和账户快照。不得把未创建的supplement_id作为批准对象。
- 审批申请生成服务端规范化参数摘要，复核人看完整计划与摘要后决定。执行时锁全部相关资源，从批准快照重建计划、核对实际金额与版本，并原子消费批准；任一变化应返回409并重新审批。
- 已存在的退款、佣金草稿、规则草稿或补款重试，分别绑定其真实资源和现有version。operation与资源类型必须匹配动作权限，不能审批任意resource_type字符串。

后续若改成“先建财务草稿、再审批、再提交”模式，需要另行设计草稿生命周期和字段；不能混用两种模式。

### 6. 下单前协议同意和交易异常

订单协议同意可以先记录为order_id为空；服务端检查本人、ORDER类型、当前报价要求的协议版本和正文哈希。创建订单的同一事务锁定同意记录，要求尚未绑定订单，再绑定本次新订单；禁止跨用户使用或被两笔并发订单重复消费。相同幂等请求重放原订单结果，不重复绑定。

报价响应明确quote_no、expires_at、服务版本、单位与数量、单价和总价、预计起止、协议版本，不承诺库存。创建成功响应返回支付截止与订单状态。支付截止、接单截止不晚于预约开始允许边界；临近开始的订单需限制最短提前量。

支付前取消：先确认没有真实成功收款；存在渠道会话时协调关单和查单，未知结果不释放仍可能支付的占位。支付后取消：按所处履约阶段创建或进入退款审核，不能直接标“退款成功”。客户端重复支付请求复用逻辑支付单，迟到成功如无法履约仍记真实收款再发起退款。

退款审批并发先预留可退额度，成功以渠道验真结果为准；部分退款是否继续服务由规则/工单结论决定。提交完成、用户确认与自动确认只推进履约，结算仍需账期与无阻断工单。已付后退款单列追偿，不能把待结算展示成负数钱包。

### 7. 核心返回字段

OpenAPI为四个目录查询和健康检查补充了与现有DTO一致的成功结构；为报价、订单摘要/详情、支付会话、支付结果、退款结果补充了规划结构。订单返回履约status、payment_status、聚合refund_status、version、截止时间和allowed_actions，用户端根据这些字段显示按钮，执行时服务端仍重验。

refund_status是多笔退款的展示汇总，不替代退款单状态；存在未决申请优先显示PENDING，全部终结后按实际累计成功额显示NONE/PARTIAL_SUCCESS/FULL_SUCCESS，只有无成功额且退款均已失败时显示FAILED。原支付PAID事实不因退款改成“未支付”。

其他业务成功data仍标x-response-contract-status=draft，不把通用Envelope当成已经细化的联调契约。前端开发某板块前，须补齐该板块请求、成功/错误响应示例和字段敏感范围。

### 8. 游客图片与私有证据

未来首页、陪练详情等公开DTO返回的图片应采用PublicMedia（asset_id+受控URL），只允许已审核、PUBLIC且用途匹配的资源；不得暴露storage_key、实名证明或工单证据。私有/media/access保持登录和归属校验，不为了游客展示放开整张资源表。

当前游戏查询实际DTO仍只有icon_asset_id，未接展示URL适配器；文档不将其伪装为已具备完整图片展示能力。接入CDN/访问服务后再补公开DTO中的URL，或另行设计仅白名单公开图片的解析接口。该决定在发现页联调前完成，本轮未新增路由。

### 9. 回调、任务与限制

第三方回调有独立的签名、证书、时间戳/防重放与渠道号校验；原始报文不能先通用JSON重编码再验签。渠道通知成功ACK由具体产品定义，不套所有业务接口的Envelope；当前回调仍为503占位，不能响应假成功。

支付查单、关单、接单超时、自动确认、认证过期、Outbox重试、结算提交和每日对账是内部任务，不向App暴露可任意触发的接口。后台创建对账只提交任务并返回任务ID/状态，不能假装已同步完成。

心跳与活跃事件实现前限制上报频率；活跃事件以event_key去重。现有路由对它们仍要求Idempotency-Key，本轮只记录该行为，不改代码。后续若要减少幂等表写入，可另行评审专用去重方案。登录、刷新、上传和公开筛选必须补速率限制与资源上限，接口设计中的429不代表当前已实现限流。

V0.2文档复查已核对180项操作、权限、内部引用、路径参数和核心类型。本次框架重建修复了路由空文件，采用main.go→api/router.go→各板块函数的结构；验证显式注册路径与文档一致、每条路由到达对应处理函数，并执行Go测试/静态检查。模型和迁移不变；未验证真实数据库或支付渠道。
