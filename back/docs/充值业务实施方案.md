# 充值业务实施方案

## 1. 文档目的

本文定义东东电竞首期“用户充值到钱包”的实施方案。首期只完成充值闭环，不在本阶段接入钱包下单、订单退款回钱包、提现、转账或多币种。

目标链路：

```text
用户创建充值请求
  → 服务端创建渠道预支付
  → 用户在渠道完成支付
  → 渠道通知或主动查单验真
  → 钱包入账
  → 用户查询余额、充值记录和钱包流水
```

本方案属于对现有范围的扩展。`接口设计.md` 当前仍写有“不扩展充值钱包”，进入开发时应同步修订总接口设计、路由清单和 OpenAPI，避免文档口径冲突。

## 2. 核心决策

### 2.1 部署边界

首期不新增独立的 Wallet Server。钱包能力部署在现有 Order Server 中，但使用独立的 `WalletService`、biz 用例和 data 仓储，避免与 `UserOrderService` 混成一个模块。

```text
dongdong-order-api
├── SystemService
├── UserOrderService
├── CoachOrderService
├── AdminOrderService
├── WalletService          # 新增
└── CallbackService
```

选择 Order Server 的原因：

- 钱包后续会参与订单扣款、冻结、解冻、退款和结算，属于交易域。
- 后续钱包扣款与订单创建可以在同一数据库事务中完成。
- 避免 Business Server 与 Order Server 之间出现分布式扣款补偿。
- 保留未来把 WalletService 独立部署的边界，不影响首期交付。

### 2.2 领域命名

- `orders`：只表示陪练服务订单。
- `recharge_packages`：表示可购买的充值套餐，连接人民币支付金额与虚拟币到账数量。
- `wallet_recharges`：表示用户充值请求，不称为服务订单，也不进入 `orders` 表。
- `wallet_accounts`：用户钱包账户及当前余额快照。
- `wallet_ledger_entries`：不可变的钱包资金流水。
- `wallet_recharge_events`：充值渠道通知、查单和处理事实。

### 2.3 不直接复用现有 payments 表

当前 `payments.order_id` 为非空，并且支付、退款状态都围绕服务订单设计。首期不为了充值而把 `payments` 改成多态关联，否则会引入 `order_id/recharge_id` 二选一约束并扩大现有交易链路的改动范围。

充值所需的渠道单号、预支付引用、渠道交易号等先保存在 `wallet_recharges`；渠道事实记录在 `wallet_recharge_events`。未来如果业务需要统一多种收款场景，再单独设计通用 `payment_intents`，不在本期提前抽象。

## 3. 首期范围

### 3.1 包含

- 每个用户一个虚拟币钱包，首期资产代码暂定为 `DD_COIN`。
- 查询钱包余额。
- 按固定充值套餐创建充值请求。
- 获取渠道预支付参数。
- 接收并验证渠道支付通知。
- 对未知结果进行主动查单和补偿。
- 充值成功后原子入账。
- 查询充值记录和钱包流水。
- 管理端查询、创建和版本化更新充值套餐。
- 管理端只读查询充值及异常状态，是否首期开放页面可另行决定。
- 基础对账、监控、审计和幂等保护。

### 3.2 不包含

- 钱包支付订单。
- 下单冻结、取消解冻和履约扣款。
- 订单退款退回钱包。
- 提现、转账、红包。
- 多种虚拟资产、余额有效期和动态兑换汇率。
- 人工直接修改余额。

任何人工资金修正都应在后续通过审批单和专用流水实现，不允许直接更新余额字段。

## 4. 分层与代码组织

建议新增：

```text
back/api/order/v1/wallet.proto

back/internal/service/order_wallet.go
back/internal/biz/wallet.go
back/internal/data/wallet.go
back/internal/model/wallet.go
back/internal/infra/recharge_provider.go
back/internal/infra/wechat_recharge.go       # 接入微信时增加
```

现有文件调整：

```text
back/internal/server/order.go                # 注册 WalletService
back/internal/server/order_policies.go       # 声明认证和幂等策略
back/internal/app/app.go                     # 注入 WalletUsecase 和渠道适配器
back/internal/model/registry.go              # 注册钱包模型
back/internal/model/enum.go                  # 增加钱包和充值状态
back/config/config.yaml                      # 增加充值渠道配置
back/api/v1/routes.json
back/api/v1/openapi.json
```

分层职责：

- service：提取当前登录用户、校验请求、映射业务错误码、组装响应。
- biz：执行充值状态机、金额规则、入账规则和幂等语义。
- data：行锁、唯一约束、事务内余额与流水更新。
- infra：渠道下单、验签、解密通知、主动查单；不得直接更新钱包。

## 5. 数据模型

所有金额统一使用定点十进制，严禁使用浮点数：

- 真实支付、钱包余额、订单价格、退款和结算金额统一使用 `DECIMAL(20,2)`。
- 充值套餐倍率使用 `DECIMAL(10,4)`，计算结果统一四舍五入到两位小数。
- Go 代码直接使用 `github.com/shopspring/decimal` 的 `decimal.Decimal`，不额外封装金额类型。
- Protobuf 和 JSON 的 Decimal 字段统一使用十进制字符串，例如 `"31.50"`。
- 充值到账金额按充值金额乘以套餐倍率计算：`credited_amount = Round(pay_amount * package_multiplier, 2)`。

### 5.1 recharge_packages

充值套餐由运营配置，用户只能购买启用且在有效期内的套餐。

|字段|类型|说明|
|---|---|---|
|id|bigint|主键|
|name|varchar(64)|套餐名称|
|pay_amount|decimal(20,2)|真实支付金额|
|currency|char(3)|首期固定 CNY|
|package_multiplier|decimal(10,4)|套餐倍率，`1.0500` 表示到账金额增加5%|
|credited_amount|decimal(20,2)|套餐预计到账金额快照|
|asset_code|varchar(32)|首期固定 DD_COIN|
|status|varchar(16)|ENABLED/DISABLED|
|effective_at|timestamptz nullable|生效时间|
|expired_at|timestamptz nullable|失效时间|
|version|integer|配置版本|
|created_at|timestamptz|创建时间|
|updated_at|timestamptz|更新时间|

约束：

```text
pay_amount > 0
package_multiplier >= 1.0000
package_multiplier <= 10.0000
credited_amount = ROUND(pay_amount * package_multiplier, 2)
version > 0
```

充值时必须把支付金额、套餐倍率和最终到账金额复制到充值单，不能依赖套餐当前值复算历史充值。

### 5.2 wallet_accounts

每个用户一个钱包账户。

|字段|类型|说明|
|---|---|---|
|user_id|bigint|用户ID，同时作为钱包主键；一名用户对应一个钱包|
|asset_code|varchar(32)|首期固定 DD_COIN|
|available_balance|decimal(20,2)|可用钱包余额，首期充值只增加该字段|
|frozen_balance|decimal(20,2)|冻结钱包余额，首期保持0，为订单阶段预留|
|status|varchar(16)|ACTIVE/FROZEN/CLOSED|
|version|integer|并发更新版本|
|created_at|timestamptz|创建时间|
|updated_at|timestamptz|更新时间|

约束：

```text
PRIMARY KEY(user_id)
available_balance >= 0
frozen_balance >= 0
version > 0
```

钱包可以在首次查询时创建，也可以在首次成功充值事务中创建。推荐在首次成功充值时使用“查询或创建后加行锁”，避免登录即产生大量无余额账户。钱包不再分配独立 `wallet_id`，所有归属和关联直接使用 `user_id`；`asset_code` 是钱包资产属性，不用于创建同一用户的第二个钱包。

### 5.3 wallet_recharges

充值请求及渠道支付状态。

|字段|类型|说明|
|---|---|---|
|id|bigint|主键|
|recharge_no|varchar(40)|服务端充值编号，唯一|
|user_id|bigint|发起用户|
|package_id|bigint|下单时选择的充值套餐|
|package_version|integer|套餐版本快照|
|pay_amount|decimal(20,2)|人民币支付金额快照，>0|
|currency|char(3)|固定 CNY|
|package_multiplier|decimal(10,4)|套餐倍率快照|
|credited_amount|decimal(20,2)|实际到账钱包金额|
|asset_code|varchar(32)|固定 DD_COIN|
|provider|varchar(32)|WECHAT 等渠道代码|
|merchant_id|varchar(64)|服务端选择的商户号|
|app_id|varchar(64)|服务端选择的应用ID|
|out_trade_no|varchar(64)|发送给渠道的商户单号，唯一|
|provider_transaction_id|varchar(128) nullable|渠道交易号|
|status|varchar(24)|充值状态|
|prepay_ref_cipher|bytea nullable|预支付引用密文|
|failure_code|varchar(64) nullable|稳定失败分类，不保存敏感原文|
|expires_at|timestamptz|支付截止时间|
|paid_at|timestamptz nullable|渠道确认支付时间|
|credited_at|timestamptz nullable|钱包入账时间|
|version|integer|状态迁移版本|
|created_at|timestamptz|创建时间|
|updated_at|timestamptz|更新时间|

状态：

```text
PENDING
PREPAY_CREATED
SUCCEEDED
CLOSING
CLOSED
FAILED
```

关键约束：

```text
UNIQUE(recharge_no)
UNIQUE(provider, merchant_id, out_trade_no)
UNIQUE(provider, merchant_id, provider_transaction_id) WHERE provider_transaction_id IS NOT NULL
pay_amount > 0
package_multiplier >= 1.0000
package_multiplier <= 10.0000
credited_amount = ROUND(pay_amount * package_multiplier, 2)
version > 0
```

### 5.4 wallet_ledger_entries

钱包资金事实，只允许插入，不允许更新或删除。

|字段|类型|说明|
|---|---|---|
|id|bigint|主键|
|user_id|bigint|钱包所属用户，也是钱包主键|
|asset_code|varchar(32)|虚拟资产代码|
|entry_type|varchar(32)|首期为 RECHARGE_CREDIT|
|biz_type|varchar(32)|RECHARGE|
|biz_id|bigint|wallet_recharges.id|
|available_delta|decimal(20,2)|可用余额变化|
|frozen_delta|decimal(20,2)|冻结余额变化，首期为0|
|available_after|decimal(20,2)|变化后可用余额快照|
|frozen_after|decimal(20,2)|变化后冻结余额快照|
|occurred_at|timestamptz|资金事实时间|
|created_at|timestamptz|记录创建时间|

关键约束：

```text
UNIQUE(user_id, asset_code, entry_type, biz_type, biz_id)
available_after >= 0
frozen_after >= 0
```

首期充值流水必须满足：

```text
available_delta = wallet_recharges.credited_amount
frozen_delta = 0.00
```

### 5.5 wallet_recharge_events

保存渠道通知和主动查单事实，便于去重、重试和审计。

|字段|类型|说明|
|---|---|---|
|id|bigint|主键|
|recharge_id|bigint nullable|未匹配到充值单时可空|
|provider|varchar(32)|渠道|
|merchant_id|varchar(64)|商户号|
|event_key|varchar(160)|渠道通知ID或主动查单唯一键|
|event_type|varchar(32)|PAY_NOTIFY/QUERY/CLOSE|
|payload_digest|varchar(64)|原始报文摘要|
|payload_asset_id|bigint nullable|加密原始报文引用|
|status|varchar(16)|RECEIVED/PROCESSED/RETRY/REJECTED|
|error_code|varchar(64) nullable|稳定错误分类|
|handled_at|timestamptz nullable|处理完成时间|
|created_at|timestamptz|接收时间|

关键约束：

```text
UNIQUE(provider, merchant_id, event_key)
```

## 6. API 设计

建议在 `api/order/v1/wallet.proto` 中定义 `WalletService`。

### 6.1 用户接口

#### 查询钱包

```http
GET /api/v1/wallet
Authorization: Bearer <token>
```

响应 `data`：

```json
{
  "asset_code": "DD_COIN",
  "available_balance": "31.50",
  "frozen_balance": "0.00",
  "status": "ACTIVE"
}
```

钱包余额保留两位小数，并在 Protobuf 和 JSON 中使用十进制字符串传输，前端按两位小数展示。

#### 查询充值套餐

```http
GET /api/v1/wallet/recharge-packages
Authorization: Bearer <token>
```

响应包含套餐 ID、人民币售价、套餐倍率、预计到账金额和资产代码。所有 Decimal 字段一律使用字符串传输。

#### 创建充值

```http
POST /api/v1/wallet/recharges
Authorization: Bearer <token>
Idempotency-Key: <key>
Content-Type: application/json

{
  "package_id": "3",
  "provider": "WECHAT",
  "client_type": "WECHAT_APP"
}
```

服务端不接受自定义到账金额、`user_id`、`merchant_id`、`app_id`、支付成功状态或渠道交易号。服务端必须根据 `package_id` 读取有效套餐，按套餐公式计算到账金额并生成快照。

响应 `data`：

```json
{
  "recharge_id": "123",
  "recharge_no": "RC...",
  "package_id": "3",
  "pay_amount": "30.00",
  "currency": "CNY",
  "package_multiplier": "1.0500",
  "credited_amount": "31.50",
  "asset_code": "DD_COIN",
  "status": "PREPAY_CREATED",
  "expires_at": "2026-01-01T12:30:00+08:00",
  "payment_params": {}
}
```

`payment_params` 由渠道适配器返回，只允许当前客户端完成支付所需的白名单字段，不返回商户密钥或内部签名材料。

#### 查询充值详情

```http
GET /api/v1/wallet/recharges/{recharge_id}
Authorization: Bearer <token>
```

只允许查询本人充值记录。

#### 查询充值列表

```http
GET /api/v1/wallet/recharges?page_size=20&cursor=<cursor>&status=<status>
Authorization: Bearer <token>
```

列表响应由服务端同时返回数据库状态和面向用户的展示状态：

```json
{
  "items": [
    {
      "id": "123",
      "recharge_no": "WR...",
      "pay_amount": "30.00",
      "credited_amount": "31.50",
      "status": "PREPAY_CREATED",
      "display_status": "PENDING_PAYMENT",
      "can_pay": true,
      "can_retry": false,
      "created_at": "2026-01-01T12:00:00Z",
      "expires_at": "2026-01-01T12:30:00Z"
    }
  ],
  "next_cursor": "",
  "server_time": "2026-01-01T12:10:00Z"
}
```

展示状态映射：

- `PENDING` 且未过期：`CREATING`。
- `PREPAY_CREATED` 且未过期：`PENDING_PAYMENT`，`can_pay=true`。
- 本地已过期的 `PENDING/PREPAY_CREATED` 或数据库状态 `CLOSING`：`CONFIRMING`，不再允许继续拉起旧支付参数。
- `SUCCEEDED`：`SUCCEEDED`。
- `CLOSED`：`EXPIRED`，`can_retry=true` 表示可以重新创建新充值单，不复用原单。
- `FAILED`：`FAILED`，`can_retry=true`。

#### 查询钱包流水

```http
GET /api/v1/wallet/transactions?page_size=20&cursor=<cursor>&type=RECHARGE_CREDIT
Authorization: Bearer <token>
```

### 6.2 渠道回调

```http
POST /api/v1/callbacks/wallet/{provider}
```

回调接口不使用用户 Bearer Token。必须由渠道适配器完成：

- 读取原始请求字节。
- 验签和必要的报文解密。
- 校验商户号、应用ID、币种、金额和商户单号。
- 生成稳定 `event_key` 并去重。
- 返回渠道规定的成功或失败 ACK，不返回通用业务 Envelope 代替渠道 ACK。

未完成验签和可信入账时不得返回成功 ACK。

### 6.3 管理端充值套餐

```http
GET  /api/v1/admin/wallet/recharge-packages
POST /api/v1/admin/wallet/recharge-packages
PUT  /api/v1/admin/wallet/recharge-packages/{package_id}
Authorization: Bearer <admin-token>
```

- 查询权限为 `wallet.recharge.read`，创建和更新权限为 `wallet.recharge.write`。
- 创建和更新必须携带 `Idempotency-Key`。
- 更新必须提交当前 `version`，服务端使用乐观锁并将版本递增。
- 管理端只提交支付金额和套餐倍率，`credited_amount` 始终由服务端按统一公式计算。
- 已被充值单引用的历史套餐快照不随套餐修改而变化。

## 7. 充值状态机

```text
PENDING
  ├── 创建预支付成功 ──> PREPAY_CREATED
  ├── 创建失败且不可重试 ──> FAILED
  └── 超时未创建 ──> CLOSED

PREPAY_CREATED
  ├── 渠道确认支付且入账成功 ──> SUCCEEDED
  ├── 用户未支付并超时 ──> CLOSING ──> CLOSED
  └── 渠道明确失败 ──> FAILED

SUCCEEDED 为终态，重复通知只返回同一处理结果，不重复入账。
```

未知结果不能直接标记 FAILED 或 CLOSED，应进入重试查单。只有渠道明确未支付、已关闭或超过补偿期限后才能关闭。

## 8. 核心事务

### 8.1 创建充值请求

1. 从认证上下文获取 `user_id`。
2. 读取启用且在有效期内的充值套餐，校验钱包账户状态。
3. 在事务中读取或创建 `idempotency_keys`。
4. 使用 `shopspring/decimal` 计算 `credited_amount = pay_amount * package_multiplier`，统一四舍五入到两位小数。
5. 把套餐版本、人民币支付金额、套餐倍率和最终到账金额复制到 `wallet_recharges(PENDING)`。
6. 提交事务。
7. 调用渠道创建预支付。
8. 使用版本条件把状态更新为 `PREPAY_CREATED`，保存加密预支付引用。
9. 渠道调用超时但结果未知时，不创建第二个商户单号；通过原 `out_trade_no` 主动查单或重试。

渠道调用不放入数据库长事务，避免持锁等待网络。

### 8.2 充值成功入账

渠道通知验真后，在同一个数据库事务中：

```text
1. 插入 wallet_recharge_events；唯一冲突表示重复事件。
2. SELECT wallet_recharges ... FOR UPDATE。
3. 核对 user、merchant、app、out_trade_no、currency 和渠道支付金额；渠道支付金额只与充值单的 `pay_amount` 比较。
4. 如果充值单已 SUCCEEDED，确认交易号一致后按成功幂等返回。
5. 如果状态不允许成功迁移，记录事件为 REJECTED 并终止。
6. SELECT wallet_accounts ... FOR UPDATE；不存在则创建后重新锁定。
7. 使用 Decimal 计算 `available_balance + credited_amount`，结果量化为两位小数并检查数据库精度范围。
8. 将 `credited_amount` 增加到 `available_balance` 并更新 version。
9. 插入唯一的 RECHARGE_CREDIT 流水。
10. 更新充值单为 SUCCEEDED，记录 transaction_id、paid_at、credited_at。
11. 更新事件为 PROCESSED。
12. 提交事务后返回渠道成功 ACK。
```

余额更新、流水插入和充值单成功必须全部成功或全部回滚。

## 9. 幂等与并发

### 9.1 用户请求幂等

- `POST /wallet/recharges` 必须要求 `Idempotency-Key`。
- 幂等记录范围至少包含 `actor_type=USER`、`actor_id`、`operation=wallet.createRecharge`、`key`。
- 保存请求参数哈希；相同键但套餐或渠道不同返回409。
- 相同键重放返回原充值单及当前状态，不创建新的渠道单号。

### 9.2 渠道通知幂等

- 首层使用 `(provider, merchant_id, event_key)` 去重。
- 第二层使用 `(provider, merchant_id, provider_transaction_id)` 防止同一真实支付匹配多张充值单。
- 第三层使用钱包流水唯一键防止重复入账。

### 9.3 钱包并发

- 余额更新前锁定 `wallet_accounts` 行。
- 锁顺序固定为：充值单 → 钱包账户 → 钱包流水/事件。
- 后续订单接入时统一锁顺序，避免充值和下单并发死锁。
- 所有余额计算使用 `decimal.Decimal`，入库前统一 `Round(2)` 并检查 `DECIMAL(20,2)` 范围。

## 10. 渠道适配器

biz 层只依赖抽象接口，不直接依赖微信 SDK：

```text
CreateRecharge(ctx, request) -> prepay result
VerifyCallback(ctx, raw request) -> verified event
QueryRecharge(ctx, out_trade_no) -> verified result
CloseRecharge(ctx, out_trade_no) -> close result
BuildACK(result) -> provider-specific response
```

适配器返回的结果必须区分：

- 明确成功。
- 明确未支付或已关闭。
- 明确失败。
- 结果未知、可重试。

超时、网络错误和解析异常不能自动等同于支付失败。

配置建议：

```yaml
wallet:
  asset_code: DD_COIN
  recharge_expire: 30m

wallet_payment:
  provider: WECHAT
  merchant_id:
  app_id:
  api_v3_key:
  merchant_cert_serial:
  merchant_private_key_path:
  platform_cert_path:
  notify_url:
  timeout: 5s
```

密钥和证书通过环境变量或受控密钥系统注入，不提交到仓库，不写入日志。

## 11. 查询、对账与补偿

### 11.1 主动查单任务

定时扫描：

- `PREPAY_CREATED` 且接近或超过支付截止时间的充值单。
- 已收到通知但处理状态为 `RETRY` 的事件。
- 渠道返回未知结果的充值单。

查单确认成功后复用同一个入账事务，不另写一套余额逻辑。

首期先实现独立的超时关单循环：扫描已超过 `expires_at` 的 `PENDING/PREPAY_CREATED`，通过 `status + version` 抢占为 `CLOSING`，再执行渠道查单。渠道确认已支付时复用充值入账事务；确认未支付时先调用渠道关单，成功后再写 `CLOSED`；网络错误、未知状态和缺少渠道适配器时保留 `CLOSING`，按最短重试间隔再次处理。`CLOSING` 仍允许可信支付通知或查单结果迁移到 `SUCCEEDED`，避免关单与晚到通知竞态造成漏入账。

管理端充值单查询、事件 `RETRY` 补偿、批次游标、退避上限和人工复核仍放在最后阶段实现。

### 11.2 每日对账

首期至少校验：

- 渠道成功交易是否都对应 `wallet_recharges.SUCCEEDED`。
- 每个成功充值是否恰好有一条 `RECHARGE_CREDIT`。
- 充值单 `pay_amount` 与渠道支付金额是否一致。
- 充值单 `credited_amount` 与钱包流水增量是否一致。
- `wallet_accounts.available_balance/frozen_balance` 是否与钱包流水重放结果一致。

发现差异时生成异常记录和告警，不自动直接改余额。

## 12. 错误码建议

|场景|HTTP|业务码建议|说明|
|---|---:|---:|---|
|金额或渠道参数非法|400|1001|InvalidArgument|
|未登录|401|1100|AuthRequired|
|钱包被冻结或关闭|403|新增钱包状态码|不能创建充值|
|充值单不存在或非本人|404|1002|不泄露他人资源|
|幂等键参数冲突|409|新增幂等冲突码|相同键不同请求|
|充值状态冲突|409|新增充值状态码|非法状态迁移|
|渠道未配置|503|1202 或新增充值渠道码|配置缺失|
|渠道结果未知|503|新增可重试码|客户端查询原充值单|
|内部事务失败|500|5000|不返回原始错误|

业务码的最终编号在实现前统一补充到 `业务状态码.md` 和 `internal/ecode`。

## 13. 安全与隐私

- 充值金额、用户和渠道商户配置完全由服务端校验。
- 回调验签必须使用原始请求体，验签前不能重新序列化。
- 日志不得记录签名密钥、预支付密文、完整渠道报文或用户敏感身份信息。
- 返回给用户的充值记录不包含商户密钥、证书序列之外的内部配置和原始回调。
- 原始渠道报文如需留存，应加密保存到私有资源，并在事件表只保存摘要和资源引用。
- 管理员查询需独立权限，例如 `wallet.read`、`wallet.recharge.read`，首期不提供直接余额修改权限。

## 14. 监控指标

建议增加：

- 创建充值请求数及成功率。
- 渠道预支付调用耗时和错误分类。
- 支付通知验签失败数。
- 重复通知数。
- 充值成功到钱包入账的延迟。
- 充值成功但未发现流水的数量，目标必须为0。
- 钱包余额与流水重放不一致数量，目标必须为0。
- 主动查单积压量和最老积压时间。
- 每日充值金额、成功笔数、失败笔数和关闭笔数。

日志统一携带 `request_id`、`recharge_no`、`provider` 和脱敏后的渠道事件标识，不记录密钥和敏感原文。

## 15. 测试方案

### 15.1 biz 单元测试

- 套餐有效期、支付金额、倍率和币种校验。
- Decimal 乘法、两位小数量化和边界金额校验。
- 合法/非法充值状态迁移。
- 同一幂等键重放。
- 相同幂等键不同参数冲突。
- 成功、失败、关闭、未知渠道结果映射。

### 15.2 data 事务测试

- 首次充值并发创建唯一钱包。
- 同一渠道通知并发处理只入账一次。
- 同一渠道交易号不能入账到不同充值单。
- 余额、流水、充值状态任一步失败时全部回滚。
- 超出 `DECIMAL(20,2)` 范围的余额计算被拒绝。
- 余额约束和流水不可变约束生效。

### 15.3 infra 渠道测试

- 正确验签和解密。
- 签名错误、时间戳过期、商户号不匹配。
- 金额、币种、应用ID和商户单号不匹配。
- 重复通知。
- HTTP 超时、5xx、畸形响应和未知状态。
- 主动查单成功、未支付、关闭、未知结果。

### 15.4 service/HTTP 测试

- 未登录访问拒绝。
- 不允许客户端提交 user_id、商户号或成功状态。
- 创建充值必须提供幂等键。
- 只能查询本人充值记录。
- 响应不泄露渠道敏感字段。
- 渠道回调返回渠道要求的 ACK。

### 15.5 验收场景

1. 用户购买支付金额 `30.00`、倍率 `1.0500` 的套餐，渠道成功后钱包准确增加 `31.50`。
2. 同一回调发送10次，钱包仍只增加 `31.50`。
3. 两个并发回调处理同一交易，只能有一个事务写入资金流水。
4. 回调金额与充值单不一致时不入账并产生告警。
5. 渠道回调丢失后，主动查单可以完成入账。
6. 数据库入账失败时不向渠道确认已完成处理，后续重试能够恢复。
7. 用户只能查询自己的余额、充值单和流水。
8. 钱包余额等于全部已处理钱包流水的重放结果。

## 16. 实施阶段

### 阶段一：契约与模型

- 确认充值渠道和客户端类型。
- 确认固定充值套餐、倍率和上下架策略。
- 新增 wallet proto、路由和 OpenAPI。
- 新增五张表、枚举、索引和约束。
- 将五个钱包模型注册到 `model.AllModels()`，由现有 GORM `AutoMigrate` 完成建表和索引同步。

### 阶段二：本地钱包闭环

- 实现 WalletService、WalletUsecase 和 WalletRepo。
- 实现钱包查询、充值创建、详情、列表和流水查询。
- 使用假的渠道适配器完成状态机和事务测试。
- 完成幂等键参数哈希和结果重放。
- 完成用户充值列表展示状态、可支付/可重试标记和服务端时间。
- 完成专用超时关单循环、渠道查单后关单以及 `CLOSING -> SUCCEEDED` 竞态保护。

### 阶段三：真实渠道

- 接入微信或选定渠道的预支付和支付回调能力。
- 完成证书、密钥、通知地址和环境配置。
- 完成渠道沙箱或测试商户联调。
- 完成渠道 ACK 测试。

### 阶段四：对账与上线

- 完成日对账和异常告警。
- 进行并发、故障注入和重复回调测试。
- 灰度开放充值入口。
- 监控首批充值的渠道金额、充值单、流水和余额一致性。

### 阶段五：充值单管理查询与补偿任务（最后实施）

- 增加管理端充值单列表、详情和异常状态筛选。
- 增加回调事件 `RETRY`、渠道未知结果等通用补偿任务；专用超时关单循环已在阶段二完成。
- 增加补偿任务的批次、游标、重试次数和退避控制。
- 增加异常充值告警、人工复核入口和处理审计。
- 完成补偿任务与渠道查单、关闭接口的故障测试。

该阶段按当前决策放在充值业务最后实施；在此前阶段只运行充值安全闭环必需的专用超时关单循环，不提前增加管理端充值单查询和通用补偿调度代码。

### 后续阶段：钱包支付订单

充值稳定后再设计：

- `ORDER_HOLD`：创建订单冻结余额。
- `ORDER_RELEASE`：拒单、取消或超时解冻。
- `ORDER_CAPTURE`：履约完成后扣除冻结余额。
- `ORDER_REFUND`：退款成功后退回可用余额。

该阶段必须与订单、预约占位、退款和陪练结算事务一起设计，不在充值首期中预先实现半套流程。

## 17. 开发前待确认项

进入编码前需要明确：

1. 首期充值渠道是微信支付、支付宝还是其他渠道。
2. 微信 App、小程序是否共用商户号，分别使用哪些 app_id。
3. 各充值套餐的支付金额、倍率和上下架时间。
4. 用户单日充值次数和累计金额限制。
5. 充值成功后是否允许用户申请“充值退款”；首期建议不开放自助接口。
6. 渠道回调原始报文的加密保存位置和保留期限。
7. 生产环境证书与密钥的注入方式。
8. 管理后台首期是否需要充值查询与异常处理页面。
9. 钱包资产的正式名称、`asset_code` 和前端展示文案。
10. 对账任务的运行时间、账单时区和异常通知方式。

在以上事项确认前，可以先完成数据库模型、领域接口、假渠道适配器和事务测试，但不应把模拟支付成功路径作为生产充值能力上线。
