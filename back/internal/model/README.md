# 东东电竞后端持久化模型

本包按照用户端、陪练师端和运营后台的共同业务实体组织，共 **55 张表**。数据库为 PostgreSQL，结构体使用 GORM v2 标签，由Kratos接口包引用。模型本身只依赖 Go 标准库，未绑定某一版 Kratos，也没有初始化整个后端工程。

## 使用边界

- `model` 是持久化结构；当前按用户指定的简化结构，由internal/api对应板块实现请求处理并读写本包，响应使用独立DTO，不直接序列化数据库模型。
- 不直接把模型序列化为客户端响应，也不把模型直接绑定请求。敏感字段已尽量标 `json:"-"`，但这不替代权限和脱敏。
- 主外键为有符号 `int64`，对外 ID 使用字符串；金额为 `int64` 分，费率为 `int32` 万分比，不使用浮点数。乘法/累计金额需防溢出。
- 可空字段使用指针，`bytea` 用 `[]byte`（nil 为 NULL）。审计 IP 用 `sql.NullString` 对应 PostgreSQL `inet`。
- `timestamptz` 保存绝对时间；连接设 UTC，展示与业务统计按 Asia/Shanghai。`Date` 保存明确日历日期，不对日期做时区转换。
- JSONB 的 SQL NULL 与 JSON 字面量 null 不混淆。数据库规定附件/风险码为数组，其余快照/配置为对象；应用层还要验证具体结构。
- 统一不使用 `gorm.Model` 与 `DeletedAt`，交易/审核历史不因软删除而被默认隐藏。字典停用、用户注销脱敏。
- 普通业务表嵌入 `Base`，GORM 正常更新时自动维护 `updated_at`；只追加事件/审计嵌入 `EventBase`，禁止自动更新时间并由触发器拒绝修改。原生 SQL、`UpdateColumn` 等绕过自动处理的写入仍须显式更新时间。版本号必须在 WHERE 校验并显式递增。

## 建表与迁移

迁移已从本包移到 `back/migrations`：按15个业务属性分组，另设基础扩展、外键两组，共17组 up/down 文件。新库按编号升序执行全部 up 文件；跨表外键最后安装，回滚按相反顺序执行 down 文件。各文件自行包事务，具体使用方法见该目录 README。

原 `PostgreSQLSchema` 和单文件 `schema.sql` 已移除。需要在Go中读取时使用 `migrations.Files`（embed.FS），由独立迁移工具选择方向、管理版本和执行。本包仅负责模型，不主动执行迁移。

**仅调用 `db.AutoMigrate(model.AllModels()...)` 无法得到完整结构。** 唯一索引、复合外键、排斥及不可变保护以版本化SQL为准；后续修改模型时新增增量迁移，不回改已执行的版本。

旧版54表数据库的升级补丁已移至 `back/migrations/legacy/002_model_review_fixes.sql`，不进入主迁移链。已用修正版55表脚本建库的数据库，本次只是拆文件，不重放建表；接入迁移工具前核对结构并登记正确基线。本次没有执行真实数据库迁移。

没有实体关联字段，刻意避免 GORM 隐式保存关联、意外级联或循环迁移。通过显式 ID 查询和事务完成关联写入。

## 本次落实的审查修正

1. 用户、陪练、服务、活动增加 `content_version`；佣金规则、业务规则等增加更新版本。内容版本与登录失效/计价版本分开。提交新内容时递增内容版本，审核记录保存该版本；回写锁定对象、核对版本及审核任务，发布时再递增，使其他基于旧版本的任务失效。
2. 可信支付成功事务创建 `SettlementItem`，状态 `SettlementItemStatusNotEligible`，初始 `payable_cent=coach_net_cent`（未确认通道费时）。确认完成只激活账期；拒单、超时退款也能引用已有基准追加调整。
3. 支付事件原始事实不可修改，但允许更新处理状态、错误、处理时间，以及首次匹配 PaymentID；普通订单/退款/工单/审计事件使用只追加触发器。
4. 退款与支付、占位与订单、订单与服务、结算明细与批次的陪练归属补复合外键；服务、游戏、区服、段位关系也做同游戏校验。
5. `ServiceCompletionPayload` 明确实际完成数量、实际结束、证据与说明。数量单位读取订单快照；按局申报需要买家确认与售后举证，模型字段不能证明真实履约。
6. 追偿增加 `RecoveredCent`，支持部分追回；SQL 限制累计追回不能超过应追回金额。
7. 实名支持 `REVOKED`、撤销时间和原因；年龄资格须同时为 `ELIGIBLE`，不能只看 PASSED。
8. 渠道原始报文增加 `CHANNEL_PAYLOAD` 用途且强制私有；DAU 活跃事件已保留，首期看板需要 DAU 时必须同时落地采集。

## 复查修正版

- Outbox 明确支持入驻、实名、技能、工单、内容审核、通知、支付、对账及配置聚合，不再仅允许订单/退款/结算。
- 资源用途增加游戏图标、Banner、活动封面、服务图片；渠道报文继续强制私有。
- 删除6个完全重复的普通索引，保留原唯一索引；其他左前缀索引不在没有查询计划时批量删除。
- `Base` 自动维护普通表更新时间；`OrderEvent`、`RefundEvent`、`CaseEvent`、`AdminAuditLog`、`UserActivityEvent` 使用 `EventBase`。支付事件含处理进度，结算调整含追偿进度，二者继续使用可变 `Base`。
- 新增 `SettlementSupplement`（`settlement_supplements`），处理首次结算成功后的补款；首次出款明细的唯一成功约束保持不变。

### 补款金额和幂等规则

例：首次成功出款80元，已批准修正将应得改为90元，追加净增10元的调整，创建独立10元补款指令；补款成功后 `paid_out_cent` 累计为90元，原80元成功出款不修改。

1. 仅首次出款已经 SUCCESS 的应结记录可创建补款；否则正向调整直接进入首次结算的应付金额，不能额外重复补款。
2. 一个调整最多一条补款指令，由 `adjustment_id` 唯一约束保障；复合外键保障调整、应结、陪练与收款账户归属一致。
3. 创建/提交补款时按统一顺序锁应结记录与调整，核验已批准正向调整（CORRECTION/REVERSAL/FEE）、账户渠道、审批金额/哈希及无未决退款或阻断工单。净增额为 `coach_delta_cent-channel_fee_delta_cent`，必须大于0。
4. 指令金额不得超过该调整的净增额，也不得超过 `max(payable_cent-paid_out_cent-其他未终结补款预留,0)`。PENDING/SUBMITTED/PROCESSING 和可重试 FAILED 指令继续占额度；只有已证明不会成功且明确终止的 CANCELLED 才释放。不能把未知渠道结果标 FAILED 或 CANCELLED。
5. 每次提交及失败重试均复核上述条件。同一指令重试沿用 `request_no`；重试安全性依渠道幂等规则确认，不换请求号重新打款。每次请求/查询/通知追加 SYSTEM 审计和受控报文引用。
6. 可信成功结果在同一事务 CAS 将补款推进 SUCCESS、累计 `paid_out_cent`、写审计及 Outbox。重复回调读取已有 SUCCESS 后返回，不重复累计。历史首次出款表保持不变。
7. SUCCESS/CANCELLED 为指令终态；数据库保护指令金额、账户快照、审批和请求号不可更改。失败后的更换账户/通道需要另行设计人工冲正与重建流程，首期仅支持原指令幂等重试，不直接修改失败指令的收款方。
8. 已结算收益和对账导出要合并 `settlement_batch_items.SUCCESS` 与 `settlement_supplements.SUCCESS`；渠道账单仍按各自独立请求号识别；通知业务类型和对账差异本地对象类型均支持 `SETTLEMENT_SUPPLEMENT`，避免与原应结记录 ID 混淆。应结总览通过累计 `paid_out_cent` 展示，补款进度另查独立表。

以上跨行余额、批准与状态迁移校验由后续 biz/data 事务用例实现，本包只提供字段、约束和不可变保护，不宣称已经实现出款服务。

## 仍需在事务用例中实现的规则

模型和约束不能替代以下业务代码；本次没有创建这些后端用例：

- 下单校验报价的买家、服务、区服、数量和有效版本；游戏/服务/认证/账户有效；禁止给自己下单。
- 入驻申请的实名用户与陪练用户一致；区分实名普通重试失败和明确撤销；接单同时校验有效实名、年龄、技能及所有仍生效处罚。
- 创建订单与修改排期先锁同一陪练，校验完整 OPEN 时间覆盖，再创建占位。所有链路统一锁顺序：陪练 → 订单 → 支付 → 应结 → 退款/出款明细。
- 创建待支付订单时保证待支付截止、接单截止与预约开始的边界；临近开始的订单要限制最短提前量。获取业务锁后用实际时间校验截止，不使用事务开始时刻代替当前时间。
- 同一事务校验支付、预留退款额度、推进状态与写事件/Outbox。未知渠道结果不能释放额度或新建重复出款。
- 结算调整汇总：`net_adjustment_cent=Σcoach_delta_cent`；`channel_fee_cent=Σchannel_fee_delta_cent`；`payable_cent=max(coach_net_cent+net_adjustment_cent-channel_fee_cent,0)`。费用不得重复扣减，超过应得的费用责任按规则另外记追偿，不阻止真实退款记账。
- 待结算展示 `max(payable_cent-paid_out_cent,0)`；出款后退款的待追偿单列，追偿金额由实际费用分担、成功出款/回退事实计算，不能将负数展示成钱包余额。不得修改历史成功出款金额。
- 核验批次总额等于其明细之和、账户渠道一致、应结满足账期及无未决退款/阻断工单；处理出款成功需幂等累计 `paid_out_cent`。
- 敏感审批执行时锁资源，核对版本、参数哈希、批准有效期和双人身份；批准不能被改参数复用。
- 数据库触发器只保护指定事实表，不自动实现整个业务状态机；生产运行账号仍应最小授权，表所有者与迁移账号分离。
- 事件仅插入；普通表正常 GORM 更新自动维护时间，原生 SQL/UpdateColumn 仍显式更新 `updated_at`。GORM `Updates(struct)` 可能跳过 false/0，涉及开关、归零与状态时使用 map 或显式 Select。
